### 1. CodeAct 执行边界（二选一裁决 → 选 A：实现独立可杀执行进程 + 资源限制）

**实现（Claim：已实现且已验证）**

- `src/synapse/runtime/subprocess_executor.py`：每步 CodeAct 在一次性子进程内求值（子进程内仍跑
  smolagents `LocalPythonExecutor`，语言语义/白名单与进程内模式一致）；父进程持有 wall-clock，超时
  `kill+wait` 强杀；POSIX 经 `preexec_fn` 施加 `RLIMIT_AS / RLIMIT_CPU / RLIMIT_FSIZE / RLIMIT_CORE`；
  Windows 无 `resource` 模块自动降级为仅超时+强杀（能力边界如实声明）；子进程 cwd 为一次性临时目录。
- `src/synapse/runtime/exec_child.py`：子进程执行体（stdin JSON 载荷 → stdout 单行 JSON 信封；state 经
  pickle b64 通道跨步保持；不经 `-m`、不 import synapse，与 venv 安装方式零耦合）。
- `Config` 新增：`codeact_executor: local|subprocess`（枚举校验，typo 构造即 `ConfigError`）、
  `codeact_timeout_s=30`、`codeact_memory_mb=2048`、`codeact_cpu_s=120`。默认 `local`（历史口径零回归，
  `build_team` 仅在 subprocess 档注入执行器）。
- CNR 能力验证真探针（`team.py::_make_verify_check_fn`）：从「声明即已验证」改为实测
  `final_answer(2 ** 10)` 并核对结果（local 档进程内求值 / subprocess 档真拉起隔离子进程）；探针失败
  该能力诚实不通过验证；结果闭包记忆化。**边界如实（复审修正）**：该探针只证明最小 CodeAct 执行
  可用（不验证超时强杀/RLIMIT/隔离属性），且当前是**握手期的验证记录**——verified 结果不 gate 后续
  `execu.run()` 的执行路由（真正门控留后续）；记忆化生命周期=本闭包=本 run_task 的 Scheduler/CNR，
  即**每个任务的 hello 周期探测一次**（TTL 300s 单任务内不过期；subprocess 档每任务多一次约 1.8s
  的子进程冷启动）。

**复审修正（两路独立审查后已修复，附测试锁定）**：

- 每 Agent 独立 executor 实例（原实现 4 个 CodeAgent 共享同一实例 → 一个角色的 CodeAct 变量残留进
  其他角色 state，跨 Agent 串扰已实测复现；现每 Agent 各建实例 + 隔离测试 +
  `len({id(...)})==4` 断言）。
- 序列化通道错误语义：父侧 state **逐 key 过滤**（个别不可 pickle 值只丢该键，不再整体变 None 拖垮
  子进程）；不可 pickle 的 **final answer 显式 `SerializationError`**（不再静默 repr 降级——子进程通道
  仅支持可 pickle 结果）；非 final 中间结果 repr 降级且信封打标；state 回传解码失败=显式协议错误；
  子进程回传丢弃键计数（`state_dropped`）入信封透明化。
- Config 资源参数正值校验（`codeact_timeout_s/memory_mb/cpu_s ≤ 0` 构造即 `ConfigError`）。
- 测试收紧：白名单拦截断言钉住 `not allowed/authorized` 语义（原 `failed` 匹配会掩盖子进程任意崩溃）。

**性能边界（Windows 开发机实测，2026-08-31）**：一次性子进程每步拉起+import smolagents 约
**1.9–2.0s/步**（local 档同代码 <2ms）；mock 单任务端到端 **9.56s（subprocess）vs 0.02s（local）**；
CNR 探针一次约 1.78s。10 轮 mock 约 +95s——故 subprocess 档默认关闭，**不宜在无说明的情况下用于
时延敏感评测**（openEuler/Linux 容器内冷启动低于 Windows，未单独量化）。中期的每 run 常驻 worker

### 已验证边界

- 长度前缀 framing，能够从流式分块中恢复消息边界；
- 并发 `send` 串行化，前缀和载荷不会交错；
- 连接、发送、接收与 `accept` 超时会转为显式 `TransportTimeout`；
- `sendall` 超时可能留下半帧，发送端会立即关闭已失步连接，后续发送显式失败；
- 对端不存在、崩溃/关闭、半帧截断、超限帧均显式失败；
- `close()` 可重复调用，关闭后发送/接收不会静默成功；
- 演示探针覆盖握手、能力发现、路由、关闭全链路。

### 不承诺的能力

本实现不是跨平台 IPC 声明，也不包含背压策略与自动重连。上述两项保留为 P1 后续；
调用方必须自行决定队列上限、重试预算和幂等语义。

### V3-02 对账提醒

当前 `Scheduler + UnixSocketTransport` 已测试 `transport_bytes = 4 + len(wire)`，即按
真实帧长计量；`InProcessTransport` 不产生 4 字节 socket framing。V3-02 落地后仍须按
其最终口径补齐 `transport = Σ帧长`、`logical = Σ(header + payload)` 的组合对账，当前
`Scheduler.send()` 返回的本地 Agent 仅表达路由意图，不代表远端已接收或处理。
