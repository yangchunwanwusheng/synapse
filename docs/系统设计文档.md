## 2. 总体架构（五层）

自上而下五层，核心反馈环：共享记忆累积 → 预测基更准 → 残差更稀疏 → 非文本字节更省。

```
┌─ ① 多 Agent 运行时 ────────────────────────────────────────────┐
│   Planner · Retriever · Executor·CodeAct · Summarizer           │
│   smolagents 基座 · Model 抽象（OpenAIServerModel / MockChatModel）│
├─ ② 协议解析与调度 ──────────────────────────────────────────────┤
│   Message Schema{action,params,result,capability,handles}       │
│   CNR 握手/能力发现 · 言语行为选择器 tell/ask/write/hold · Scheduler │
├─ ③ 状态交换·数据平面（M4 非文本状态传递核心）─────────────────────┤
│   CAS 内容寻址库 · 预测基 · 预测残差编码(句向量)                  │
│   校验和(hash 不符→回退 ask(full))                              │
├─ ④ 共享记忆与检索 ──────────────────────────────────────────────┤   反馈环:
│   MemoryUnit+元数据 · 混合检索 · 预测基 · 巩固器                  │ ◀ 记忆↑→预测基更准
├─ ⑤ 评测与度量 ─────────────────────────────────────────────────┤   →残差更稀疏→字节更省
│   双模式 A/B · 字节/时延/质量/命中率 · 非文本字节轨迹              │
└─ 底座 openEuler 24.03-LTS-SP3 ─────────────────────────────────┘
    依赖轻纯Python | FAISS/Milvus(可选) | IPC/共享内存/Socket | WASM/容器沙箱 | eBPF
```

## 3. 核心数据结构（代码契约）

### 3.1 能力描述 Capability（M2 握手/能力发现）
```python
@dataclass(frozen=True)
class Capability:
    agent_id: str
    role: str                  # "planner"|"retriever"|"executor"|"summarizer"
    actions: tuple[str, ...]   # 支持的 ActionType
    encodings: tuple[str, ...] # "text"|"embedding"|"residual"|"hidden"（CNR 协商用）
    model_family: str          # 同族判定（隐状态零拷贝前提）
```

### 3.2 结构化消息 Message（M2，禁纯文本透传）
```python
@dataclass
class Message:
    msg_id: str
    sender: str
    receiver: str
    action: str                # ActionType 枚举：PLAN/RETRIEVE/EXECUTE/SUMMARIZE/
                               #   TELL/ASK/WRITE/HOLD/HELLO/CAP_QUERY/CAP_REPLY
    params: dict               # 输入参数（高密度语义单元）
    result: dict | None        # 返回结果
    capability: Capability | None   # 仅握手/能力发现消息携带
    handles: tuple[str, ...]   # CAS 句柄（非文本载荷引用，残差/句向量）
    payload_kind: str          # "text"|"embedding"|"residual"|"hidden"|"none"
    checksum: str | None       # hash(Y)，校验回退用
    text: str | None           # 文本载荷（text 模式或回退时）
    meta: dict                 # wire_bytes/tokens/ts 等度量埋点
```
- 结构化模式下，`text` 仅承载**不可结构化的少量自然语言**；协作语义走 `action/params/result/handles`，**不得**把全部协作信息塞进 `text`。

### 3.3 记忆单元 MemoryUnit（M5 元数据齐全）
```python
@dataclass
class MemoryUnit:
    mem_id: str                # M5 记忆 ID（内容寻址 hash 或 uuid）
    source_agent: str          # M5 来源 Agent
    created_at: str            # M5 创建时间（ISO8601）
    task_topic: str            # M5 任务主题
    summary: str               # M5 摘要描述
    kind: str                  # "evidence"|"strategy"|"conclusion"|"plan"|"experience"
    content: str               # 完整内容（证据链/结论/策略片段）
    tags: tuple[str, ...]      # M6 标签检索
    embedding: list[float]|None# M6 语义检索 + 预测基载体
    task_id: str
    reuse_count: int = 0       # 复用计数（命中率统计）
```

### 3.4 残差包 ResidualPacket（M4 非文本载体）
```python
@dataclass
class ResidualPacket:
    base_handle: str|None      # 接收方可复现的预测基（记忆锚点）的 CAS 句柄
    residual: bytes            # 量化/稀疏化后的残差 z = Y − Ŷ
    dim: int
    nnz: int                   # 非零残差分量数（越小越省）
    checksum: str              # hash(量化后的 Y)；接收重构后比对
    orig_bytes: int            # 原始全量字节（用于 M8 节省统计）
```

## 4. 模块详设

### ① 多 Agent 运行时 `runtime/`（M1）
- **`team.py::build_team`**：构造 4 个 smolagents `CodeAgent`（Planner / Retriever / Executor / Summarizer），每个附 `role`/`agent_id`/`cap`（Capability）属性，复用既有 `Scheduler` + CNR。
- **`runtime/model.py`（smolagents `Model`）**：实现 `MockChatModel`（确定性、离线、供 smoke/CI；按角色出 CodeAct）与 `make_model`（mock | 任意 OpenAI 兼容后端，如 paratera/vectorengine，OpenAIServerModel；key 仅来自 `.env`，严禁硬编码；`!= "mock"` 即走真实 API 路径，支持平台零改动切换）。

### ② 协议解析与调度 `protocol/`（M2）
- **`messages.py`**：`ActionType` 枚举、`Message`/`Capability` 序列化（`to_wire()`/`header_bytes()`/`text_bytes()` 计线缆字节）。
- **`handshake.py::CNR`（Capability Negotiation & Resolution）**：
  - `hello()` 广播 `Capability`；`discover()` 收集对端能力；`negotiate(sender, receiver) -> encoding`：取双方 `encodings` 交集的**最高密度**（hidden>residual>embedding>text），同族才允许 hidden；异构降级到 embedding/text（协议映射）。
- **`scheduler.py::Scheduler`**：路由消息、驱动一轮协作（plan→retrieve→execute→summarize），记录消息计数/时序到 `Metrics`。

### ③ 状态交换·数据平面 `stateplane/`（M4 核心）
- **`cas.py::CAS`**：`put(data: bytes) -> handle`、`get(handle) -> bytes`；内容寻址，消息只带句柄不透传 blob。
- **`embedding.py::Embedder`**：本地 sentence-embedding，`encode(texts)->vecs`；离线 `HashEmbedder` 兜底（确定性、无依赖，供 smoke）。
- **`residual.py::ResidualCodec`（M4 的"生成/接收"核心）**：
  - `encode(Y_vec, B_hat_vec) -> ResidualPacket`：按 |残差分量| 降序贪心加入，到失真目标 cos(Ŷ,Y)≥threshold 即止 → 只传必要分量；附 `checksum=hash(量化Y)`。索引字节宽自适应（dim≤256 用 1B，2048 维用 2B）。
  - `decode(pkt, B_hat_vec) -> Y_hat`：Ŷ+残差 重构。
  - `verify(Y_hat, Y_true) -> bool`：cos(Ŷ, Y_true) ≥ 阈值；不符→调用方回退取全量文本。
- **`checksum.py`（M4 正确性保障）**：`digest_ints()`/`digest_bytes()`；校验不符则回退，保证端到端不静默出错。

### ④ 共享记忆与检索 `memory/`（M5/M6）
- **`store.py::MemoryStore`**：`write(unit)`、`get(mem_id)`、`upsert_prototype()`、JSON 持久化；`write` 自动补 `created_at`、算 `embedding`、生成 `mem_id`（内容寻址去重）。
- **`retrieval.py::HybridRetriever`（M6）**：`search(query, k=5) -> list[(unit, score)]`，融合 关键词倒排 + 标签过滤 + 向量余弦（加权）；命中即 `reuse_count += 1`（喂 M8 命中率）。
- **`tom.py::ToMPredictor`**：`estimate(receiver_id, query) -> B_hat_vec`——从接收方共享记忆检索聚合预测基向量；`best_base(results, target)` 择与 target 最接近的候选作预测基。
- **`consolidate.py::Consolidator`**：跨任务按 topic 取 embedding 均值并归一化建原型单元，使记忆朝任务分布收敛（更优预测基 → 残差更稀疏）。

### ⑤ 评测与度量 `eval/`（M8）
- **`metrics.py::Metrics`**：累计 `messages`、`text_tokens`/`text_chars`、`nontext_transfers`/`nontext_bytes`、`latency_s`、`memory_hits`/`memory_queries`（命中率）、`quality`；`improvement()` 对比双模式（含 token/字节节省百分比）。
- **`harness.py::ABRunner`（M3）**：同任务跑 `text` 与 `synapse` 两模式，连续 ≥10 轮，输出每轮 Metrics 轨迹 + 非文本字节轨迹（`contraction_bytes`）。

## 5. 双模式对照（M3）

| 维度 | text 模式（基线） | synapse 模式 |
|---|---|---|
| 通信媒介 | 全量自然语言文本 | 结构化 `Message` + 残差句柄 |
| 中间状态 | 内部态→文本→内部态往返 | 句向量预测残差直传（M4） |
| 记忆 | 无/每次从头 | 共享 MemoryUnit + 混合检索复用（M5/M6） |
| 正确性 | 文本无损 | 有损残差 + 校验回退（端到端正确） |
| 度量 | tokens/chars/latency | + 非文本字节/命中率/非文本字节轨迹（M8） |

## 6. 关键流程

### 6.1 一轮协作（端到端）
`Scheduler` 驱动：Planner 拆计划 → Retriever 检索（查共享记忆，命中则复用）→ Executor·CodeAct 计算 → Summarizer 汇总 → 高价值中间态 `WRITE` 回记忆。每步消息经 §② 结构化，度量埋点入 `Metrics`。

### 6.2 非文本状态传递四环节（M4 点名要求，以 Retriever→Summarizer 传长证据为例）
- **生成**：Retriever 取证据的句向量 Y；预测基 B̂ = 接收方共享记忆中与查询相关单元的向量；`ResidualCodec.encode` 出残差（只传必要分量 → 字节小，区别于发全量向量）。
- **传递**：`Message{action=TELL, handles=[cas.put(残差), cas.put(证据正文)], payload_kind="residual", checksum=hash(Y)}`；CAS 只传句柄，不透传 blob。
- **接收**：Summarizer 按句柄从共享 CAS 取回证据正文（非线缆透传），重嵌入得真值 Y_true；`ResidualCodec.decode` 用同一预测基重构 Ŷ；`verify` cos(Ŷ,Y_true)≥阈值？不符→回退取全量文本。
- **使用**：证据正文直接喂给后续 Agent 生成，省"内部态→文本→内部态"往返。

## 8. 残余风险与设计取舍
- 字节节省幅度依赖任务间共享结构 → 任务族刻意构造（G1/G2 关联）+ 负例族（无共享结构）证因果区分。
- 异构模型不可共享隐状态 → 残差句向量路径为默认主路（黑盒 API 适用），hidden 零拷贝为可选加分项。
- 非文本"常更大"的误解 → 发**预测残差**（只传必要分量）而非全量向量（M4 设计的关键，见 §6.2）。

## 9. CNR 与 A2A Agent Card 协议映射（M2 协议映射机制）

赛题 M2 点名要求"握手、能力发现**或协议映射机制**"。2025 年 [Agent 互操作协议综述](https://arxiv.org/abs/2505.02279) 确立了四大业界标准：MCP（工具调用）、ACP（REST 多模态消息）、**A2A（基于 Agent Card 的能力发现与对等任务委派）**、ANP（去中心化发现）。SYNAPSE 的 `Capability{agent_id, role, actions, encodings, model_family, probe}` 与 A2A Agent Card 在概念上一一对应，本节给出字段级映射，落实"协议映射"赛题要求。

### 9.1 字段级对照表

| SYNAPSE Capability | A2A Agent Card 字段 | 说明 |
|---|---|---|
| `agent_id` | `name` / `id` | Agent 唯一标识 |
| `role` (planner/retriever/executor/summarizer) | `skills[]` | Agent 承担的角色/技能 |
| `actions` (PLAN/RETRIEVE/EXECUTE/...) | `capabilities` (actions 接口) | 支持的动作集合 |
| `encodings` (text/embedding/residual/hidden) | **（A2A 无此维度）** | **SYNAPSE 增量扩展**：非文本编码分档协商 |
| `model_family` | **（A2A 无此维度）** | SYNAPSE 增量：同族判定（hidden 零拷贝前提） |
| `probe` (codeact_sandbox) | **（A2A 无此维度）** | SYNAPSE 增量：运行时可验证承诺（§2.2 check_fn 门控） |
| CNR `hello` / `discover` | A2A `tasks/send` 发现流程 | Agent 注册与能力广播 |
| CNR `negotiate` | **（A2A 无对应）** | SYNAPSE 增量：编码档位协商 |

### 9.2 SYNAPSE 对 A2A 的扩展

A2A 的 Agent Card 聚焦"谁有能力做什么动作"，其能力描述停留在**动作层**。SYNAPSE 的核心增量是 `encodings` 协商维度——它把能力发现从"动作可否"推进到"**非文本状态以何种编码档位传递**"：

- A2A 回答：Retriever 能不能向 Summarizer 发证据？（动作层）
- CNR 回答：Retriever 和 Summarizer 之间用 residual / embedding / text 哪一档编码传递证据？（编码层）

`negotiate` 取双方 `encodings` 交集中**最高密度**的一档（hidden>residual>embedding>text），异构自动降级——这是 A2A 没有的、专属于"低开销非文本状态传递"赛题的协议维度。`probe` + check_fn 进一步把能力从"声明"升格为"运行时可验证承诺"（借鉴 hermes `registry.py` 的 check_fn 门控）。

> 这一节同时回答了赛题"协议映射机制"要求，并展示了团队对业界标准的把握——SYNAPSE 不是另起炉灶，而是 A2A 在"非文本状态传递"方向上的可互操作扩展。

## 10. 状态传递的三轴自我定位 + 中间态隔离谱系

### 10.1 三轴定位（对照 [latent 通信统一框架综述](https://arxiv.org/abs/2606.05711)）

综述按 WHAT × WHICH × HOW 组织了 18 种 latent 通信代表方法，但整个体系聚焦白盒场景。SYNAPSE 在三轴上的自我定位：

| 轴 | 白盒代表方法 | SYNAPSE 定位 |
|---|---|---|
| **WHAT**（传什么） | KV-Cache / 隐状态 | **embedding 级（句向量）**——黑盒 API 可得，无需访问模型内部 |
| **WHICH**（收发如何对齐） | 层对齐（同架构同层） | **无需层对齐**——收发方只需共享同一 embedder，异构 LLM 也成立 |
| **HOW**（如何融合） | cross-attention / 投影适配器 | **预测基 + 残差重构**（Ŷ = B̂ + z）——数学运算，无神经网络适配器 |

### 10.2 黑盒空白区：SYNAPSE 的坐标

| 方法 | 载体 | 需白盒? | 需训练? | 效果 |
|---|---|:---:|:---:|---|
| C2C (ICLR'26) | KV-Cache 投影融合 | 是 | 是 | +3.1–5.4% 精度，2.5× 加速 |
| LatentMAS (ICML'26) | 末层隐向量 + KV-cache 转移 | 是 | 否 | 省 70.8–83.7% token，+14.6%，4× 加速 |
| HyLaT | latent-文本混合协议 | 是 | 部分 | 平衡效率与鲁棒性 |
| **SYNAPSE（本作品）** | **句向量预测残差 + CAS 句柄 + 校验回退** | **否** | **否** | HotpotQA/MuSiQue 省 71–81% token，ΔF1≥0 |

综述确认黑盒 API（无法访问隐状态）场景基本是空白，LatentMAS 也明确承认"要求同架构、不兼容闭源 API"是其硬局限。SYNAPSE 的残差路线只依赖句向量（黑盒可得）+ 接收方共享记忆作预测基（Wyner-Ziv 边信息视角），**恰好落在这个空白区**。更关键的是：所有 KV 方案传的是定长/线性增长的 cache，SYNAPSE 传的是**随协作经验收缩的残差**——"传输量随记忆积累递减"是 SYNAPSE 独有的、所有白盒 KV 方案都不具备的特性。

## 11. 共享记忆的拓扑定位与治理语义

### 11.1 拓扑定位：黑板式中心共享（为何不是分布式）

研究界把多 Agent 记忆拓扑分三类：① 各 Agent 本地记忆；② 中心化黑板式共享；③ 混合（本地感知 + 共享世界态）。SYNAPSE 是**黑板式中心共享**——`MemoryStore` 是所有 Agent 共享的单一存储。

这个选择不是工程便利，而是**机制必然**：残差编码要求"接收方可复现的预测基"，预测基 B̂ 必须是接收方在解码时能再次取回的同一向量。只有中心化共享记忆能让发送方与接收方对"B̂ 是什么"达成一致——若记忆分布式，发送方选的 B̂ 接收方取不到，残差解码失败。**中心化是残差编码成立的前提**，而非可优化项。

### 11.2 写入治理与溯源语义

对照 [Governed Shared Memory](https://arxiv.org/html/2606.24535v1) 与 hermes swarm 黑板的 `{key, value, _authors}` 溯源模型，SYNAPSE 的治理语义如下：

- **内容寻址幂等**：`mem_id = hash(source_agent | task_topic | content)`，相同内容天然去重，避免多 Agent 重复写入同一知识。
- **作者可溯**：每条 `MemoryUnit.source_agent` 记录产生者，多 Agent 冲突时可追溯。
- **原型覆盖**：`upsert_prototype` 同 topic 覆盖，旧原型 `superseded_by` 标记——冲突 = 原型覆盖 + 作者可溯（而非数据丢失）。

### 11.3 演化链即治理审计链（§3.1 A-MEM 风格）

借鉴 [A-MEM](https://arxiv.org/) 的动态链接 + 取代检测，SYNAPSE 的记忆不是"永不删除、无限堆积"，而是带演化链的活性记忆体：

- **`links` 字段**：新记忆写入时记录其取代/相关的旧记忆 `mem_id`，形成可追溯的演化链。
- **`superseded_by` 字段**：被取代的旧记忆标记，检索默认过滤（不再召回过时记忆），但**不删除**——演化链完整保留，构成天然审计链。
- **检索过滤 + 链接扩展**：`HybridRetriever.search` 跳过已取代单元，同时沿 `links` 以小权重补进关联单元，扩大有效召回而不引入过时信息。

这直接回应了"永不删除、无限增长"的架构短板：记忆从**追加**变为**演化**，且每一次演化（谁取代了谁、何时、为何）都可审计。对 G2 关联演进任务组而言，记忆不是历史快照，而是随任务推进持续精化的活体知识。
